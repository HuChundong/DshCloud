# 把 agent 放进沙箱，实际要付的代价

[English](sandbox-pitfalls.md) | 中文

这里每一条都是真把这套部署搞坏过的东西，附上暴露它的现象，以及最终定性的那个测量值或报错。
按所属层次分组——因为那决定了谁能修它。

有几条连同「正确结论之前那个错误结论」一并记下。那几条才是有用的：故障从来不在它看起来在的地方。

## 模板是镜像**运行中**状态的快照

CubeSandbox 的模板不是镜像。它是镜像运行时拍下的快照，为每个租户还原一次——所以 `CMD` 启动的
任何东西都会被冻进去，在任何租户存在之前就启动了，且每个还原出来的沙箱里一模一样。

第一版把后端放进了 `CMD`。沙箱起来时带着一个在**另一台机器的生命周期里**启动过的后端，持有
另一台机器的状态，然后立刻退出。当时的直觉——多往模板里烘焙一些东西好让启动更快——恰好是
反的：模板装不下任何「只有租户到来时才知道」的东西。

因此镜像不声明 `CMD`。`cube-entrypoint.sh` 只守着 envd，由网关在拿到那份只在创建时才存在的
身份之后，通过 envd 的进程 API 为每个租户启动后端。

**多花一轮才发现的推论：** `POST /templates/{id}` 不会拾取新镜像。把已有模板指向新镜像，每个
沙箱还原的仍是它原来那份快照。换镜像就必须建新模板，每次都是。

## envd 交给进程的是一个干净环境

后端从 `CMD` 改由 envd 启动之后，Dockerfile 里每一行 `ENV` 都悄无声息地不再抵达它。后端跑在
`HOME=/root`、没有权限模式的状态下——也就是说，它在一个「存在的意义就是被随便写」的容器里，
带着没有任何浏览器能回答的审批提示运行。

没有任何东西大声报错。沙箱起来了，隧道拨通了，然后第一次工具调用挂在一个无处可去的提示上。

现在镜像把自己的环境投影进一个文件、由入口脚本 source。这个文件是从**值**生成的而不是重写一遍，
所以它不可能与仍然是唯一出处的那些 `ENV` 行漂移：

```dockerfile
RUN for name in DSH_BIN DSH_HOME HOME DSH_PERMISSION_MODE NODE_ENV \
                NODE_EXTRA_CA_CERTS TZ; do \
      printf 'export %s=%s\n' "$name" "$(printenv "$name")"; \
    done > /app/sandbox/env.sh
```

`TZ` 是很晚才加进这个列表的，而且只是因为——每个文件的时间都差八小时，总会有人发现。

## 网络默认拒绝运行它的那套基础设施

CubeSandbox 默认允许公网出站，同时把私有网段一并拒绝，使沙箱无法借它的互联网访问去够到托管它
的基础设施。而网关恰好落在这些网段之一：于是沙箱够得到模型 API，却够不到启动它的那个东西。

网关的地址在创建时被显式放行，与附加网络策略是同一次调用。是地址而不是域名：`allowOut` 里的
DNS 名只有在配合 `0.0.0.0/0` 全拒规则时才生效，而那条规则会把其余一切一起拒掉。

## 模型密钥可以扣下，但没法「有条件地」扣

CubeEgress 终止 TLS 来改写 `Authorization` 头，因此沙箱里拿到的是占位符，真实密钥从不进入。
这一点要紧，是因为里面的 agent 以租户的名义拥有完全权限：环境里、文件系统里、进程表里的任何
东西，都是能被提示词读回来的东西。而一个从来不在那里的密钥，读不回来。

试图在这上面做聪明事，撞出两条约束：

- **拦截以信任为前提。** CubeEgress 为请求的 SNI 现签叶子证书，所以沙箱必须信任该安装自己的
  根证书——而 Node 只验它自带的根、忽略系统信任库，所以光装 CA 还不够，还要 `NODE_EXTRA_CA_CERTS`。
- **注入不能有条件。** 本意是只在请求带着占位符时才注入，这样自己配了密钥的租户不会被覆盖。
  但 `ngx.req.clear_header` 总是先执行，等规则能去看的时候，已经没有东西可看了。

## S3 不是文件系统，而 agent 会立刻察觉

给每个租户持久化存储，最直白的办法是把 S3 桶里属于他的前缀挂起来。s3fs 和 `rclone mount` 都
试过。两者都不可用，原因与速度毫无关系：它们把文件系统调用映射成对象调用，而 S3 没有硬链接。

harness 通过「把临时文件硬链接覆盖到正式文件上」来原子替换会话日志。于是每一轮都立刻结束于

```
EIO: i/o error, link '…session.jsonl.zstd.tmp' -> '…session.jsonl.zstd'
```

而且一条 assistant 消息都没有。

**那个错误结论：** 认为在对象存储上做持久化这条路走不通。并不是。JuiceFS 是一个恰好把数据放在
对象存储里的**文件系统**——元数据存在事务型数据库里，所以硬链接、原子改名、文件锁都还是它们
本来的含义，对象存储只负责装数据块。错在从「S3 做不到这件事」推出「这件事在 S3 上做不到」，
而正确的修法是：别再拿这个问题去问 S3。

## 需要「取回来」的卷，不算卷

JuiceFS 的第一版为每个卷创建一个磁盘镜像，在沙箱创建时挂载。它能用，而且把这个平台存在的意义
毁掉了。

| | attach 耗时 |
|---|---|
| 不挂卷 | 0.39s、0.53s |
| 每次 attach 取磁盘镜像 | 7.92s、8.29s |
| 一次共享挂载 + 每卷一个 bind | 0.06s |

沙箱从快照还原不到半秒。于是 attach 路径上任何做拷贝、下载、或启动进程的动作，都会成为整个系统
里最慢的一环——差一个数量级。

所以每个节点只挂一个 JuiceFS 客户端，每个卷是它内部某个目录的 bind mount。bind 是一次系统调用：
没有字节移动，而且沙箱只看得见属于自己的那个目录。

## 挂载点撒谎的两种方式

两次都花掉一轮排查，而且形状相同：你最自然会去问的那个问题，本身就是会失败的调用之一。

**丢失了元数据库的客户端**仍然把挂载留在挂载表里，并对每一次调用回 `EIO`。`mountpoint` 说
「挂着呢」。检查必须是一次「会失败的读」，修复必须是卸载——往一个死挂载上再挂一次毫无作用。

**由已被替换的客户端建立的 bind** 对一切回 `ENOTCONN`，而且没有任何东西会重建它：挂载表里
还列着它，于是 attach 跳过重绑，把一个死挂载交给沙箱。租户的后端随后卡在 `mkdir '/workspace'`，
表现为 `session.create` 返回 500。

这一条试了三次才对，因为每一种探测本身都是会失败的调用：

- `mountpoint -q` 会把这种 bind 报告为**未挂载**，于是最显然的那道判断根本不触发。
- 对它 `mkdir -p` 会以 `ENOTCONN` 失败，在 `set -e` 下直接终止钩子，修复代码还没轮到执行。

真正可行的检测是读 `/proc/self/mounts`——内核从内存作答——再配一次会失败的调用：

```sh
if grep -qF " ${mnt} " /proc/self/mounts && ! ls "$mnt" > /dev/null 2>&1; then
    umount -l "$mnt"
fi
```

## 插件契约比产品需要的窄

CubeSandbox 的 VolumePlugin 在每个钩子里收到的，是一个 volume id 和一个名字。没有容量、没有
大小、没有自定义参数——而且文档明确写着：插件必须仅凭 volume id 定位后端资源，配置走配置文件
与环境变量。

这一条在相信之前验证了三遍：文档里的参数表、官方 Tencent COS 示例插件自己的参数解析、以及一次
带上 `capacity` 和 `labels` 的 API 调用——两个字段都被丢弃。

后果是按租户的配额没法从平台传进来。在上游支持在创建时传参之前，只能一个数字覆盖所有租户。
两种绕开它的设计都被否掉了，因为都比等更差：让网关直接设配额，等于把一个 120MB 的二进制和
元数据库凭据塞进那个负责认证租户的组件；让插件反过来问网关，则把一个通用插件绑死在某个产品的
HTTP 接口上。

## 按工作站尺寸设的默认值，落在共享节点上

JuiceFS 的缓存默认是 100 GiB，放在挂载者的家目录里。Cubelet 以 root 执行钩子，所以那是
`/root/.juicefs/cache`，落在 `/` 恰好所在的那个文件系统上——一个没有任何运维选择过的位置，
一个没人设过的上限，而且和其他所有东西共用一块盘。

现在两者都显式配置、且总是传入。这个大小只约束读缓存；writeback 暂存的写共用这个目录，由空闲
空间下限兜底——把它调得很小之前，值得先知道这一点。

## 时间到底花在哪

当时的直觉是元数据读是瓶颈——每次 `stat` 都要去 Postgres。测下来，这是错的。以每次小文件操作
计，本地盘是 0.06 ms：

| | 创建 | `stat` 冷 | `stat` 热 |
|---|---|---|---|
| 全部默认 | 38.13 ms | 1.0 ms | 0.007 ms |

元数据缓存本来就在生效：重复 `stat` 比冷读快 140 倍。之前那次得出相反结论的测量，用的是 shell
循环——每个文件 fork 一次 `stat`，进程开销比文件系统本身还大。

真正的开销在写，分两层：

- **每次 `close` 都在等一个对象上传完。** `--writeback` 在数据块落到本地暂存的那一刻就确认：
  38 ms → 17 ms。
- **每一次持久化的元数据提交都在等一次 WAL fsync**——实测 2.93 ms，关闭后 0.33 ms，而一次
  文件创建要花掉好几次：17 ms → 8.5 ms。

调高元数据超时，延长的是一个本就存在的缓存，而不是凭空造一个。它在这里安全，只是因为一个 volume
只挂给它租户的那一个沙箱——一个目录，一个写者。

## harness 对「自己在哪里被启动」是有意见的

其中两条花掉了实打实的排查时间：

- **dsh 从进程的工作目录取沙箱策略的 workspace 根。** 从 checkout 里启动它，就把 harness 的
  源码树变成了租户的工作区——而容器内是完全权限，于是 agent 的默认工作目录成了「运行它自己那个
  沙箱的代码」。
- **cordis 在加载时按包名解析插件**，因此一份组合需要哪些包无法从依赖图推导。`pnpm prune --prod`
  删掉过构建入口要 import 的 workspace 链接。后来改从 npm 安装时又发现，
  `@deepseek-ai/dsh-web-frontend` 沿依赖图从 CLI 包到达不了，必须显式点名。

还有一条制造出「插件加载了但什么都看不见」：**客户端模块注册表从配置树的 baseUrl 解析插件的
package.json**，且只扫描它能按名字解析到的包。按路径加载的插件只会挂载它的 host 那一半，
完全不贡献 client 半边。

`npm install <本地路径>` 是同样的故障、不同的成因：它建软链指回源码位置，Node 于是从软链指向的
地方去解析插件自己的依赖，而不是从 profile。共用的帧协议因此完全解析不到，隧道插件会死在第一次
import 上。`--install-links` 改为真实拷贝。

这两件事**构建都是绿的**。不去调用 `resolve()`，谁都看不出来。

## 「空闲」不等于「没有新请求」

沙箱在安静一段时间后被回收，因为每一个都是为一个人占着的一台机器的内存。第一版是从「最后一个
请求**开始**的时刻」算这段时间的。

而一次 agent 回合由一个请求发起，随后通过浏览器在它开始之前就已打开的 WebSocket 作答。一次长于
TTL 的回合会把自己的沙箱熬到过期，回收器在回答进行到一半时销毁它——就在租户看着输出流出的时候。

改用隧道流量判断能修好它，而这之所以可用，是因为协议里没有心跳：每一帧要么是请求、要么是响应、
要么是会话事件，所以安静就是真安静，被遗忘的浏览器标签页仍会按时被回收。将来任一端若加入保活帧，
这个信号就不再回收任何东西了。

## 唯一的能力信号，和无视它的那些界面

harness 很清楚容器里没有桌面：`host.describe().canOpenPath` 会去问平台，得到的是一台没有
显示服务器的 Linux。有两处界面查询了它并正确降级——agent preset 页把「打开位置」换成
「显示位置」，产出文件那一行干脆不渲染「在文件夹中显示」。其余的没有，而每一个都是在任何
沙箱里都不可能工作的控件：

- 设置里的「Open configuration file」判断的是 `settings.describe().hasDocument`，
  它算的是 `documentPath !== undefined`——文件是否存在，而它总是存在。`agentPreset.list`
  上同名的字段算的是 `canOpenPaths()`。两种写法必有一个是错的，而且从任一调用点都看不出
  是哪一个。
- `ui-conversation` 往自己的 chat view 里注入的 `openFile` 无条件调用 `host.openPath`，
  于是每一个产出文件 chip、每一处收尾消息里的行内路径引用，都是死链接。失败被一句
  `.catch(() => {})` 吞掉，注释说原生应用会自己弹错误框——这话没错，只是这里没有原生应用。

最锋利的证据说明这是漏了而不是取舍：deliverables 这个包在「在文件夹中显示」上判断了
`canOpenPath`，却没有在它上面两行的文件 chip 上判断。

先得出的错误结论：当时把它读成了「该藏起来的东西」，退出登录插件用一个空格子遮蔽了设置里的
那个动作，并且这样过了好几周。只有在没有任何东西可以替代时，藏起一个控件才是对的。这里有
东西可以替代——文档本身——而那次遮蔽还悄悄给一个只以一件事命名的包挂上了第三个主题，这正是
后来逼出 `dsh-sandbox-host` 与 `dsh-tenant-account` 拆分的原因。

真正够不着的是 chat view 的 `openFile`：它由拥有该视图的包注入，不是对外开放的插槽，插件
只能整个替换视图。已报到上游的
[discussion 2729](https://github.com/deepseek-ai/deepseek-harness/discussions/2729)——dsh 关闭了
issue，其 CONTRIBUTING 指定 Discussions 是报 bug 的地方，并声明目前不接受外部 PR，所以
一份报告就是本项目能做的全部。

## 共享的 `/api` 通道只接受一个 interceptor

dsh 提供两种加 RPC 端点的方式：`connection.rpc.intercept('/api', …)`，在浏览器本来就在
说话的那个通道上认领端点；以及 `connection.rpc.handle('/<name>', …)`，注册一个自己的通道。
前者显然更好——不用加路由、不用改网关、不用加 nginx location——而它不可用。`/api` 上只有
一个 interceptor 的位置，且已被 dsh 自己的 `typert-gateway` 在 base bundle 里占走。第二次
注册会抛错。

这个失败是响亮的，也就这一点好：它发生在组合期，而不是第一次上传时。但从契约上完全看不出
来——`intercept` 是有文档的公开方法，签名里没有任何地方说它只容一个——所以整套设计是在读到
`rpc-host.ts` 之前就照它写好了的。

自己一个通道最后反而是更好的形状。`/files` 在它经过的每一层都可见地是一个独立平面：一处
nginx location、网关路由里的一个分支、沙箱里的一条路由。藏在 `/api` 里的端点，这三样一样
都不是。

还要注意通道名的规则：`/^\/[A-Za-z0-9._~-]+$/`。只能一段。`/api/files` 不是合法通道，
所以一个平面无法嵌套在另一个之下。

## 没有 inject 的服务，会在「用它的地方」失败，而不是在挂载时

隧道插件 inject 了 `connection` 和 `apiProxy`，而它只有一个地方调用 `ctx.setTimeout`：
隧道断开后的重拨。cordis 拒绝一个读取方没有 inject 的服务——而且是在**读取处**拒绝，不是在
挂载时——所以那一行抛了异常，位置在一个 WebSocket close 回调里，那里没有任何东西接得住它，
于是租户的整个后端进程跟着隧道一起死了。

它活了好几周，靠的是它从外面看起来的样子：一个「网关重启时会跟着重启」的沙箱。这和人们对
网关重启的预期足够接近，以至于没人追问；验收套件也同意——它重启网关，然后检查活着的会话
仍然可用，而它确实可用，因为网关把自己刚刚杀掉的那个沙箱又建了一个。

它是被一次一次性探针翻出来的：用沙箱镜像对着一个连不上的网关地址启动。第一次 close 在几
毫秒内就到了，而不是永远不到，进程直接死在日志里。

有两点可以推广。一个只在稀有路径上被用到的依赖，是 happy path 证明不了的依赖，所以 `inject`
必须对着**每一处 `ctx` 的使用**来读，而不是对着插件启动时做的那几件事。以及：一个长得像正常
事件的故障，是最能活的那种——「跟着网关重启」不需要解释，于是它一直没被解释过。

## 能推广的部分

- **快照装不下「之后才知道」的东西。** 一切与租户相关的，都必须在还原之后才抵达。
- **干净的环境是沉默的环境。** 任何给进程换爹的机制——这里是 envd——都会丢掉镜像设过的东西，
  而且不报错。
- **答案是「做不到」时，换个问题问。** S3 没有硬链接；建在 S3 之上的文件系统有。
- **attach 路径就是启动路径。** 亚秒级还原毫无价值，如果 attach 要八秒。
- **探测会以与被探测者相同的方式失败。** 先用内核从内存作答的东西检测，再用一次会失败的调用确认。
- **先测量再优化，并且怀疑自己的测量。** 第一次基准说元数据慢；它测的其实是 `fork`。
- **构建是绿的，不能说明解析没问题。** 软链、相对的 `file:` 路径、按名解析的插件，构建都正常，
  都在第一次 import 时失败。
- **只有在没有任何东西可以替代时，才藏起一个控件。**「Open configuration file」有替代品——
  文件的内容——而藏起它把这个发现推迟了好几周。
- **公开的方法不等于可用的方法。** `rpc.intercept` 有文档、有导出，而且已经被占了。
- **`inject` 要对着每一处 `ctx` 的使用去读，而不是启动时的那几处。** 只在稀有路径上用到的
  服务，happy path 证明不了。
- **长得像正常事件的故障最能活。**「沙箱跟着网关重启」不需要解释，于是一直没被解释过。
