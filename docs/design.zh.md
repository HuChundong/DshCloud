# 设计说明

[English](design.md) | 中文

这套部署为什么长成这样。它是什么、怎么跑，见 [README](../README.zh.md)。

## 为什么 nginx 是前门

前端的 API 基址和 WebSocket 地址都由 `location.origin` 推导，所以一切都必须抵达同一个
origin。那个 origin 是 nginx：它从磁盘直接应答 `index.html`、客户端 bundle 和哈希资源，
只把需要会话的部分——`/api`、`/login`、`/logout`——代理给网关。每个请求都保持同站，
因此不涉及 CORS 层。

最初是网关在前，那让每一个静态字节都要穿过一个 Node 进程：冷加载要取 index.html 和 37 个
客户端 bundle，实测经网关每请求多出约 26% 延迟，且没有换来任何东西。

外壳仍然需要会话——未认证的访客若加载了外壳，只会看着它对 401 无限重试，因为前端并不知道
这个登录页的存在——因此 nginx 用 `auth_request` 对 `/`、`/index.html` 与 `/plugins/*`
设卡，问的是网关的 `/_auth`，后者只回状态、不回内容。

## 前端不需要沙箱

Vite 构建产物是一个外壳，不是可独立运行的应用：只有 dsh 宿主会注入
`window.__DSH_BOOT__`——那张列出客户端插件包及其版本号的入口图——也只有 dsh 宿主
会在 `/plugins` 下提供这些包。单独提供构建产物，得到的是一个所有资源都加载成功、却无法
启动的页面。

但它们不必来自一个*正在运行*的宿主。这张图描述的是一份组合，而非某个租户——这里每个沙箱
都跑同一个镜像，提供的输出逐字节相同——因此 [`web/harvest-shell.mjs`](../web/harvest-shell.mjs)
在构建期把该组合启动一次，并保存它所提供的内容。于是 web 部署持有完整前端，无论调用方的
沙箱是否在运行，界面都能加载。只有 `/api` 需要沙箱。

采集在 sandbox 镜像里运行，而不是在 builder 里，这一点至关重要：组合会随环境自适应。
拥有原生目录对话框的宿主机会组合出 `directory-picker-native`，而 Linux 容器组合出
`directory-picker-browse`，bundle 的版本号也不同，因此在别处采集会发出一个插件集与其
所对话的后端不匹配的前端。

从 web 部署到沙箱没有任何回落。web 部署没有的路径直接 404——因为未命中唯一可能意味着的
就是 web 镜像与 sandbox 镜像不匹配，而用沙箱去应答既会掩盖这一点，又会把界面字节重新放回
一个按租户存在的组件上。

这同时也清掉了唯一一个不是静态产物的前端路径。`/plugins/events` 是客户端热重载通道：
浏览器会打开并保持它，等待一个活着的宿主推送重建通知。而在租户使用期间没有任何东西会重建
这些 bundle，因此该行在 [`sandbox/cordis.patch.yml`](../sandbox/cordis.patch.yml) 中被关闭
——采集与沙箱同时应用该补丁，否则采集出的 manifest 会指名一份后端并不运行的组合。

需要会话的是应用界面——`/`、`/index.html`、`/plugins/*`——而不是外壳资源，后者不含任何
租户的数据。对它们设防毫无收益，反而会破坏浏览器按设计不携带凭据发出的那些请求：
`<link rel="manifest">` 除非标签显式声明，否则不带任何凭据，而本 `index.html` 并未声明，
于是跳转到 `/login` 的结果会以 HTML 的形式抵达 manifest 解析器。

## 为什么沙箱主动向外拨号

沙箱不需要入站可达性、不需要发布端口、也不需要改动 dsh 配置：dsh 保持其默认的环回绑定和
默认为空的 `trustedHosts`。

它还有一个值得挑明的后果。dsh 用一道围栏守卫 `/api`，把配置类方法——`settings.*`、
`credentials.*`、`agentPreset.*`、`host.pickDirectory`、`host.openPath`、
`llm.discoverModels`——钉死在环回调用方，声明的 `trustedHosts` 权威无法触达它们。
由于隧道客户端把每个请求经沙箱自身的环回接口重放，这些方法得以继续工作，因此前端的
设置页与模型页保持可用。反之，暴露沙箱端口的部署会提供普通方法，而对上述全部返回 403。

同一套改写也解除了围栏的武装。该围栏是「受困代理」防御（DNS 重绑定与跨站），从来不是
认证层——dsh 不带认证，并把远程部署的认证记为待办工作。**因此网关上的认证是保护一个会执行
shell 命令的 agent 的唯一屏障。** `/api` 之下的一切，无论 HTTP 还是 WebSocket，
未携带有效会话都会在触达隧道之前被拒。

## DSH 是依赖，不是本项目的一部分

harness 以钉住的版本从 npm 安装。这里没有任何东西去改它：本部署新增的两样东西——把沙箱
`/api` 流量送出去的隧道，以及前端本来没理由提供的退出登录控件——都是 cordis 插件，在
[`sandbox/cordis.patch.yml`](../sandbox/cordis.patch.yml) 里按名字声明，并像其他插件一样从
profile 的 `node_modules` 解析。升级 DSH 就是改一个版本号，再跑一遍验收。

每个镜像都是 [`Dockerfile`](../Dockerfile) 的一个 target，构建上下文为仓库
根目录。`deps` 阶段里一次 `npm install` 供所有镜像共用，而编译 `node-pty` 的工具链留在那个
阶段，不会进入真正运行的镜像。

`@deepseek-ai/dsh-web-frontend` 是与 `dsh` 并列显式安装的，而不是通过它带进来。cordis 在
加载时按包名解析插件，因此一份组合需要哪些包无法从依赖图推导——前端就无法从 CLI 沿依赖图
到达；将来组合若需要别的包，同样要在这里点名。

租户运行的是产物：普通 Node 跑 `lib/bin.js`，即 npm 包作为 `dsh` 发布的同一个入口。

## 前门提供 TLS

客户端插件会调用 `crypto.randomUUID`，而在以明文 HTTP 提供给 `localhost` 之外任何地址的页面上，
它是 undefined。因此以局域网或公网地址访问的部署必须走 HTTPS，否则前端在加载时就失败；nginx 同时
监听 80 和 443，两者互不跳转——nginx 知道的是自己监听的端口，而不是容器发布的那个。

默认情况下 web 容器在首次启动时按 `TLS_SAN` 自签一张证书，这足以让页面成为安全上下文，代价是一次
浏览器警告。`compose.tls.yml` 把它换成正式证书：acme.sh 走 DNS-01 签发并自行续期，这也是无法使用
80 与 443 端口的部署唯一可用的验证方式——证书绑定的是主机名而非端口，所以它在 8443 上同样有效。

## 注册与登录

没有密码。访客填入邮箱，部署把一个六位验证码寄过去，答对即可——第一次是注册，之后每次是登录。
这去掉了密码部署必须做对却总做不太对的两件事：保存，和找回；这也是为什么任何地方都没有
「忘记密码」——收不到邮件的地址，不是这套部署能替他做什么的地址。

验证码就是全部凭据，所以按凭据来守。六位数字、五次尝试、每个地址每分钟一个码，首次答对即作废，
按常数时间比较，并且无论该地址是否已有账号都给出相同的回答——索取验证码不能顺带变成一种
「谁注册过」的探测手段。

注册需要邀请码。`REGISTRATION=open` 可以撤掉这道闸门；不动它的话，新地址需要一个未使用的码，
而回访的地址什么都不需要——邀请码买的是账号，不是每一次会话。它在邮件验证码之后才被检查，
这样第一步对所有地址的回答都一样：向陌生人要邀请码、向回访租户什么都不要，会把这个表单变成
一种「谁注册过」的探测手段。

会话随后是两个 token。access token 是网关只验签、不问任何存储就能确认的 JWT，这让存储不必出现在
每一次 `/api` 调用的路径上——也正因如此它收不回来，所以只给十五分钟。refresh token 是不透明的，
记录在 Postgres 里，用一次换一个；撤销它才是退出登录、停用与删除得以生效的原因。因此「一个被撤销的
会话还能触达 shell 多久」，诚实的答案是十五分钟。

续期发生在网关，不在浏览器。前端是 dsh 自己的外壳：它不知道这些 token 的存在，遇到过期的那个
只会当成 401 无限重试。所以网关在任何注意到的请求上续期——也包括 nginx 的 `auth_request`，
这正是一个开了一夜的标签页刷新之后拿到的是可用会话、而不是登录页的原因。

## 一个存储

账号、邀请码、refresh token，以及此刻还未答复的登录验证码，全部存放在 Postgres。Redis 最初
装着这些，后来是被移除而不是并存：一旦账号必须持久化，Redis 里就什么都不剩了，而第二个存储
意味着第二份备份、第二种故障形态，以及「这套部署的数据安全吗」有两个答案而不是一个。

丢失一个账号比丢失一个会话严重。租户的工作区以账号 id 命名，因此一个消失的账号会连带带走
他们的文件——哪怕文件还好端端地躺在磁盘上。

登录验证码是唯一的短命行，它按列过期而不是靠存储过期，因此一行一旦超出其用途，对所有读取就
已经不可见了，清扫只是清理而非正确性所需。

## 用户控制台

`GATEWAY_ADMINS` 指名管理这套部署的地址。他们能进 `/admin`：谁注册了、何时注册、沙箱是否在跑、
有哪些邀请码以及被谁用掉了，还有一个生成新码的输入框。对一个账号可做两件事。停用保留账号及其所有内容，同时撤销其 token 与沙箱，因此立刻生效而不是等到下次
登录。删除则把账号、会话与沙箱一并带走。其他人在那里得到 404——控制台不是租户需要知道其存在的东西。

管理员对自己的账号不会被提供这两个动作。它们都能执行，而后者会拿走唯一的回来的路。

## 租户能留下什么

在 CubeSandbox 下，租户的工作区与历史比他们的沙箱活得久。每位租户拿到一个 volume，由 CubeSandbox
的 API 创建，并由 [`integrations/cube-volume-juicefs/`](../integrations/cube-volume-juicefs/README.md) 里的驱动挂载到 `/persist`——一个
JuiceFS 文件系统装下所有租户的目录，元数据放在 Postgres，数据块放在 S3 兼容存储里。

最早用的是宿主目录，那种做法不设任何上界：一个 `dd` 就能填满宿主磁盘，把所有租户一起带走。volume
则有两道上限——文件系统自身的容量，以及每个目录的配额——两者都由 JuiceFS 强制执行，而不是靠网关去做
一件需要被信任的算术。

`entrypoint.sh` 把 dsh 家目录中属于租户的那部分链接到 volume 上，其余留在镜像放置的位置。不包括
`profiles/`：它装着组合好的 web profile、退出登录插件，以及指向 `/src` 的 `node_modules` 符号链接，
持久化它会用一份陈旧副本盖住镜像里的那份，并在升级后留下断链。

写入在抵达对象存储之前就被确认。驱动把数据块暂存到本地盘、在后台上传，元数据库也不等自己的
fsync 就提交——两者合起来把一次小文件写入从 38ms 降到 9ms，代价是节点本身丢失时会丢掉最后一
刻的工作。测量数据与撤销这项的设置见
[`integrations/cube-volume-juicefs/README.md`](../integrations/cube-volume-juicefs/README.md#performance)。

沙箱在其隧道安静满 `SANDBOX_IDLE_TTL_MS` 后被回收。判据是安静，不是“没有新请求”：一次 agent 回合
可以跑上几个小时，而它的回答是通过回合开始之前就已建立的连接流回来的，只看请求就会把沙箱连同这次回合
的成果一起销毁。隧道里没有任何心跳帧，因此一个被遗忘的浏览器标签页只是安静地占着连接，仍会按时被回收。

volume 以账号 id 命名而非邮箱，因此一个被删除后重新注册的地址拿到的是空 volume，而不是前一位持有者
的文件。删除账号会销毁其 volume——这是唯一正确的时机：被回收的沙箱必须让它留着，因为留着正是它存在的
意义。

## 隧道是插件，不是进程

它运行在它所服务的那个 dsh 进程内部，由
[`sandbox/cordis.patch.yml`](../sandbox/cordis.patch.yml) 插入组合。补丁层针对已有 id 生效，
因此新增插件需要显式的 `insert` 列表。

它换来的主要不是每个沙箱里第二个 Node 运行时那约 22 MB，而是
`inject: ['connection', 'apiProxy']` **陈述**了 `/api` 界面何时存在——而一个独立进程只能
去探测它，并且在探测写对之前拨早了两次：一次早于 socket 开始接受连接，一次早于 API 平面
挂载完成。网关在隧道出现的瞬间就释放被挂起的浏览器请求，因此两次都影响到了真实用户。

请求仍然经由环回接口，而不是在内存中直接交给路由的处理器。dsh 的环回钉死位于共享 fetch
处理器内部，因此内存内调用同样得构造一个等价请求，还会绕过路由自身的正文上限与组合方式。
一次环回往返换来的是与浏览器完全一致的行为。

## 请求头改写

隧道对本地 dsh 重放浏览器请求时做三处改动，每一处都对应围栏的一条独立分支：

| 请求头 | 改写 | 不改写的后果 |
|---|---|---|
| `Host` | 设为 dsh 的环回权威 | 403 —— 该权威既非环回也不受信 |
| `Origin` | 移除 | 403 —— 携带的 Origin 必须等于 Host 权威 |
| `sec-fetch-site` | 移除 | 403 —— 显式的 `cross-site` 标记被直接拒绝 |

网关自身的会话 cookie 同样被剥离：认证在网关处即已了结，而转发该 cookie 会把某租户的
会话令牌置于该租户自己的 agent 可读的容器内。

WebSocket 升级走同一道围栏，因此 `/api/events.mux` 与 `/api/events.host` 需要完全相同的
改写；客户端还会额外丢弃浏览器的 `sec-websocket-*` 头，使本地握手密钥是 `ws` 自己生成、
也能自己校验的那一个。

## 会话状态存放在哪

会话保存在 Postgres 中，因此网关不持有任何磁盘状态，重启也不会把任何人登出——打开着的标签页
无法自行从会话丢失中恢复，因为前端会对 401 无限重试，而不是回到一个它一无所知的登录页。
过期是每次读取都会过滤的一个字段，而不是存储自身的淘汰机制：一行记录一旦超期就已经不可见，
删除它只是日常清理。

选择服务端存储而非自校验令牌，是因为登出必须真正生效。签名的无状态 cookie 在过期前一直
有效且无法收回，对于一个能抵达 shell 的会话来说，这是错误的性质。

## 账户分区

退出登录属于这套部署，而非 dsh：harness 没有网关租户的概念，因此它自身的组合里没有任何
东西能结束一个会话。[`packages/dsh-tenant-account`](../packages/dsh-tenant-account) 在设置里加了一个
「账户」页——调用方的名字取自 `/whoami`，控件 POST 到 `/logout`，后者撤销会话并释放其沙箱。

它是一个真正的客户端插件，注册进 `settings.section`，与随附的各页并列。有三件事让它成立，
而且每一件出错时都是静默而非响亮的：包被安装进 profile 的 `node_modules`，因为客户端模块
注册表从配置树的 baseUrl 解析插件的 package.json，且只扫描它能按名解析到的包；其 `exports`
必须包含 `./package.json`，否则该解析会被 exports 门控挡住；浏览器半边写在
`window.__ModuleLoader__` 之上，它的 `require` 就是 shell 的模块表——React 由此而来，
因此该包不需要任何构建步骤，也从不经由 node_modules 解析。

而像隧道那样按路径加载的插件，只会挂载宿主半边，完全不贡献客户端半边。

## 容器里做不到的事

dsh 是按「宿主就在使用者的桌上」造的。那里浏览器和后端共用一套文件系统，所以一个路径就够
了：值得谈论的文件本来就够得着，值得阅读的文档会用桌面关联的程序打开。把后端搬进沙箱，这个
前提就没了——而好几处界面正是建在它上面的。

harness 对此只有一个信号：`host.describe().canOpenPath`。它在这里本来就是 false，因为它
会去问平台，而平台是一台没有显示服务器的 Linux。`sandbox/cordis.patch.yml` 仍然把它写死为
`api-gateway` 上的 `nativeOpen: false`：探测出的那个正确答案，是基础镜像的巧合，日后任何往
这个容器里塞进 DISPLAY 的改动都会把它翻回去。

**查询了**这个信号的界面，已经在正确降级：agent preset 页把「打开位置」换成「显示位置」，
产出文件那一行干脆不渲染「在文件夹中显示」。**没有查询**的那些，在每一个沙箱里都是死控件：

- **设置里的「Open configuration file」** 判断的是 `settings.describe().hasDocument`，
  它报告的是文件**是否存在**——总是存在——而不是有没有东西能打开它。同名字段在
  `agentPreset.list` 里写的是 `canOpenPaths()`。两者必有一个是错的。
- **对话里的文件链接** ——一个回合末尾的产出文件行，以及正文里的行内路径引用——无条件调用
  `openFile`，失败被一句 `.catch(() => {})` 吞掉。

`dsh-sandbox-host` 用「它真正能提供的能力」替换掉第一个：一个「配置文件」页，把文档显示
出来——因为这里能交给一个人的就是文档本身，而文档放不进页眉的动作行。它腾出的那个页眉格子
留空——这个手势是被搬走了，不是被藏起来了。

第二个从插件够不着：`openFile` 是 `ui-conversation` 注入进自己 chat view 的，不是对外开放
的插槽，替换它就等于替换整个视图。那属于上游 issue 加一条被记录的限制，而不是一层补丁；见
[沙箱踩坑记](sandbox-pitfalls.zh.md)。

遮蔽一个格子必须使用**不同的** `priority`，而不是相同的：同 id 同 priority 会被直接拒绝，
导致整个插件失败而不只是那一个格子。`priority` 也不是 `order`——order 是格子内的位置，
priority 是格子的遮蔽序位，数值最小者渲染。

## 怎么把一个文件送进沙箱

在本地宿主上没人需要上传：人报一个路径，agent 去读。在这里，人能报出的路径在另一台机器上，
所以得由这套部署造一个出来。

**路径不会出现在输入框里。**第一版是写进草稿的，那是错的，而且错两遍：让人读到一条自己没打
的路径，而那个框里已经有一张同一个文件的卡片了。dsh 有更合适的位置——agent 的 inbox 接受
注入的上下文，审批通知和「附加快照」走的就是这条通道。提交时往 `next-step` 追加一条
`plugin` 来源的消息，它在被下一轮认领之前不可见，认领后渲染成一条 context 行，而不是一段
看起来像人自己说的话。把卡片从消息上摘掉，这条通知也会被撤回，所以 agent 绝不会被告知一个
人已经反悔的文件。

除这段文本外，模型侧没有任何新东西：没有新的 content block，没有 provider 契约，也不需要
和 harness 就「附件是什么」达成一致。（dsh 自己的附件平面只做图片，而且明说了——通用文件在
上游被推迟，等的正是一套生命周期与 provider 契约。）

卡片渲染在 dsh 渲染自己图片缩略图的地方：组合器卡片**内部**、输入框上方。没有插槽能到那里
——那个位置是组合器 bar 的 `accessory` 属性——所以节点是在渲染后被移过去的；而 `+` 菜单里的
「附件」组，是画在真面板上方的第二个面板。两者都是伪造，两者都按 ARIA 角色而不是哈希类名
定位，也都已报到上游；见[沙箱踩坑记](sandbox-pitfalls.zh.md)。

这些端点位于 `/files`，是 dsh 自己那套 RPC 注册表里的一个通道，而不是 `/api`。`/api` 只接受
**一个** interceptor，且已经被 dsh 的 `typert-gateway` 占着，第二次注册会在挂载时抛错。
自己一个通道的代价，是 nginx 一处 location 和网关路由里的一行，而两者对待它的方式和对待
`/api` 完全一样——认出调用方，交给他的沙箱，对上面跑什么一无所知。

上传按 4 MiB 分片，原因不是包体上限：dsh 接受 160 MiB，nginx 设的是 200。原因是隧道——
它是一条 WebSocket，把每个请求都拆成 base64 帧，所以整发的一个文件会独占它整个时长，其余
调用全部排在后面。

字节先落在暂存文件里，只有 commit 之后才可见——一个写了一半的文件被 agent 捡起来时，读起来
和写完的一模一样——并且用硬链接发布，重名时失败而不是覆盖。同一天上传的两个同名文件就是两个
文件。落点是 `<workspace>/uploads/<日期>/`，而只要租户有卷，`/workspace` 就是指向那个卷的
符号链接，所以上传的东西比收下它的那个沙箱活得久。

## 租户的 agent 拿到什么

活是在沙箱里干的，所以里面装了什么，直接决定 agent 是"能回答关于这张表的问题"还是"只能
描述这个文件"。它带着：

- agent 真正会去敲的搜索与文本工具——`rg`、`fd`、`jq`、`tree`、`patch`、`file`、`less`；
- 双向的归档——`unzip`、`zip`、`7z`、`zstd`、`bsdtar`；
- 文档——`pdftotext`、`sqlite3`，以及 `officecli`：一个二进制就能读写 xlsx/docx/pptx/pdf，
  背后不需要一整套无头办公套件；
- 连通性——`dig`、`ping`、`ip`、`nc`，这是任何人在一个「整套架构就是主动外拨」的沙箱里
  第一个要查的东西；
- 一个已经装好 pandas、duckdb、表格与 PDF 读取、pillow 和 matplotlib 的 Python；
- 以及一套中文字体——没有它，带中文标签的图渲染出来全是方块，而报错里不会出现「字体」
  两个字。

OfficeCLI 自带一份 agent 技能，镜像把它装进一个镜像自己的技能根目录
（`DSH_BUNDLED_SKILL_DIR`），而不是 `$DSH_HOME/skills`——后者是指向租户卷的符号链接，镜像
放进去的副本会被租户已有的内容遮蔽。技能由二进制在构建时写出，而不是抄一份存进本仓库：
OfficeCLI 会随自身更新这份技能，仓库里的副本会悄悄地相对 `Dockerfile` 里钉住的版本变旧。
只放基础那一份：专项技能可以由 `officecli load_skill <名字>` 按需打印，把全部十一份都放进
目录，等于为租户可能永远不会打开的十个技能，在每一次请求里都付一行描述。这个根目录的排位
低于租户自己的，所以他们同名的技能会覆盖它。

Python 是挂在 `PATH` 上的 virtualenv，不是系统解释器。Debian 把系统那个标记为外部管理，
所以在它上面 `pip install` 是设计上就会失败的，而 `--break-system-packages` 等于说这个设计
错了。venv 让租户能正常 `pip install`，且伤不到发行版的 Python——而且两个包管理器都把这套
部署的镜像源**烧进了镜像**（`/etc/pip.conf`、npm 全局配置），所以租户自己装包走的是构建时
用的同一个源，而不是干等公共索引。

代价就是那个真正要紧的数字：镜像从 617 MB 变成 1050 MB，而 CubeSandbox 模板是它的快照。
这也是为什么这份清单比它借鉴的那份短。以下都是在构建出的镜像里量过之后砍掉的：`pyarrow`
（152 MB，而 duckdb 用 58 MB 就能读 parquet）、`plotly`（42 MB，而聊天窗口能显示的是
matplotlib 已经在画的静态图）、`libgl1`（41 个包的 OpenGL，这里没有任何东西经它绘图）、
`unar`（18 个包的 GNUstep，读的归档 `bsdtar` 都能读）。每一个都只差一条安装命令。

完全没拿的：数据库驱动——一个部署的数据库不是另一个部署的数据库；以及编译器——这里每个
wheel 都有对应平台的预编译版，而从源码构建是唯一需要租户自己张罗的事。

## 侧边栏的底部

那里放着两样东西，谁归哪个包，判据和别处一样：把网关拿掉，这件事还需要吗？

**沙箱行**——一个状态点加 CPU / 内存 / 磁盘三个环——属于 `dsh-sandbox-host`，因为它描述的
就是沙箱。数字来自沙箱内的 `/proc` 与 `statfs`，走上传用的同一条 `/files` 通道，有人在看
的时候每五秒拉一次。改成推送要在隧道协议里加一种帧、并让网关持有每个租户的状态；而拉取的
代价是一次很小的往返，没有页面打开时则是零。

折叠成 56px 窄条时，这一行**什么都不渲染**。第一版在那里留了一个孤立的状态点，读起来像
一个误落的记号：旁边没有任何字说明这个颜色是关于沙箱的，而它所代表的三个环在那个宽度下也
放不下。

「是否在运行」刻意不由它回答。一个没在运行的沙箱什么都答不出来，而网关本来就用 503 说了这
件事——所以状态是从「这次调用有没有到达」读出来的，那是这个问题唯一不靠猜的版本。

**账户行**属于 `dsh-tenant-account`，它占的正是原先「设置」控件的位置。这不是装饰：外壳的
设置按钮**就是** `settings.trigger` 这个座位，由拥有者包在那个打开面板的 button 里。把账户行
填进这个座位，就是把「设置」从一级控件降为它背后菜单里的一行，而面板本身和里面每一个分区都
原封不动。菜单打开面板的方式是去点拥有者自己的那个 button——`open` 是设置外壳内部的 state，
没有服务也没有事件够得着，那次点击是唯一的接缝。

## 沙箱内的权限

沙箱以 `DSH_PERMISSION_MODE=danger-full-access` 运行，base bundle 会用这一个变量同时决定
文件策略与审批策略：完全访问，且不弹审批。让租户逐条批准写入和命令，等于在一个本就用来
被写入的盒子内部设防，而审批提示在无头容器里也无处显示。真正起作用的边界是容器本身，
以及它前面的网关。

## 隔离

一位用户获得一个沙箱。没有任何东西把两位用户复用进同一个 dsh 进程，因为 dsh 没有租户
概念：它的 `/api` 界面是单一占用的，会话存储是进程级的。租户之间的隔离是容器隔离，
而网关分配每一个隧道流 id，因此沙箱只能应答为其自身租户开启的流。

## 验证

```sh
./verify.sh                                              # the Docker simulation
SANDBOX_RUNTIME=cube COMPOSE_FILE=compose.yml:compose.cube.yml \
  GATEWAY=https://host:8443 ./verify.sh                  # CubeSandbox
```

它让两个租户登录，并检查这套部署存在的意义所在的那些性质：未认证的调用与升级被拒绝、
每个租户获得各自的沙箱、后端只监听环回因而隧道是抵达它的唯一途径、被钉死在环回的配置方法在
隧道改写下依然可用、两条 `/api` 下行均能打开、一次真实模型轮次得以完成，以及任一租户都无法
列出、读取或向另一租户的会话发送提示。若运行时会扣下模型密钥，它还会检查沙箱里只有占位符。

它对两种运行时都能跑。凡是关于沙箱的提问都经由四个函数，因为这两种运行时没有任何共同的可检视
对象：在 `docker` 下沙箱是它自己所在宿主机上的一个容器，在 `cube` 下则是一台只有网关容器够得到
的机器——所以那些调用要经过一个拷贝进网关容器的 helper。而它所提的问题是从后端进程本身读取的，
不是从旁边的一个 shell 读的，因为两种运行时启动那个进程的方式不同，问 shell 得到的是另一个进程
的答案。

它还会删除所有沙箱，并检查 `/` 仍带着 boot manifest 应答、客户端 bundle 仍可获取、
未知前端路径返回 404 而不是抵达沙箱，且这些请求都没有启动任何沙箱——这正是前端拆分存在
的意义。

随后它驱动一个真实的 Chromium：登录、在无 console 与页面错误的前提下启动页面、选择工作区、
发送一条消息，并从 DOM 中读出模型的回答。这个套件的存在理由是：状态码分辨不出可用页面与
白屏——真正影响到用户的那两个故障，一个损坏的内联脚本和一个缺失的 boot manifest，
对上面每一项 HTTP 检查都是不可见的。

有一项检查不启动任何沙箱：空闲回收判定的是流逝的时间，因此直接驱动它、把它依据的两个时钟都交给
测试传入，而不是干等满一个 TTL。

依赖 `ws` 的套件在网关容器内运行。浏览器套件在宿主机装有 Playwright 时于宿主机运行，否则在
Playwright 官方镜像里运行——正是这一点让它能在部署机上跑，而不只是在开发者的 checkout 里。
两者都会消耗真实的模型 token。
